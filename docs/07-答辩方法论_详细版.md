# 07 · 答辩方法论与问答准备

> 本文是面向评审老师的解说稿：项目定位、L3 交付方法、从头到尾的执行流程、10 个高频问题与现场注意事项。
> 文中企业、人物、数据均为教学虚构；所有数字以仓库内文档、代码与测试为准。

---

## 一、先给结论：这个项目到底是什么

一句话：**它不是一个“保洁管理系统”，而是一条从客户原话到亏损归因的证据链。**

客户要的不是 8 张表，是“西乡塘为什么连亏 14 个月、到底亏在哪”。所以 5 个模块的设计是 **4 个数据入口 + 1 个出口**：每单、每笔赔付、每个阿姨、每个客户是入口，片区损益是出口。代码、测试、文档、Agent 库，都是为了让这个出口“算得平、下钻得到、说得清”。

现场可复跑的三条硬证据：

- `npm run test:run`：15 个测试文件 / 143 例全绿；
- `npm run build`：57 modules 构建成功；
- `npm run check:mp`：小程序结构与共享内核校验通过；`main` 已推送全部里程碑提交。

项目真正的强项有四个：

1. 诊断数字闭合：3.38 = 1.40 + 1.30 + 0.68；9% + 13 点 = 22%；
2. 范围克制：2 片区、5 模块、10 项明确不做；
3. 规则纯函数化 + 确定性种子，结果可复现；
4. 文档主动标注假设、偏差和未验证项。

需要提前想好怎么答的薄弱点也有四个：

- 没有真实后端、鉴权和并发，生产就绪只到 Bronze；
- 浏览器交互没有 DOM 自动化；
- 工单是 1800 单而不是文档里的 5200 单；
- 青秀三项漏损按 0 处理，是对照口径不是真实数据；
- “客户真在用”在考核场景里只能靠可运行系统 + 演示脚本模拟 UAT，不能硬说成真实客户上线。

## 二、方法论骨架：L3 交付飞轮

这套方法可以概括成四层：

| 层 | 谁在做 | 做什么 |
| --- | --- | --- |
| 判断层 | 我 | 定问题、定范围、定验收、定边界 |
| 执行层 | 8 个 Agent | PM、架构、前端、后端、QA、设计、DevOps、项目总监，按 brief 产出 |
| 资产层 | 代码库 + Agent 库 + SOP | 契约文档、纯函数、确定性种子、Agent 五段定义、过程记录 |
| 验证层 | 门禁 | A1–A10、143 例测试、`npm run verify`、对账闭合、人工演示 |

L3 的判别法不是“AI 帮我写了多少代码”，而是：**把我拿走两周，交付是否继续；换一个会写代码的人拿这套资产，结果是否一致。** 这句话建议在答辩开场就讲，它能把“你是不是自己写的”这个问题提前化解一半。

## 三、从头到尾的 8 步流程

### 第 0 步：定位（0–5 分钟）

先完成身份切换：我不是程序员，我是项目总监。我的价值不是写页面，而是判断“做什么、不做什么、什么叫对、怎么证明对”。

产出：一句交付哲学——“人只做判断，Agent 做执行，代码库 + Agent 库 + SOP 做记忆，门禁做质量。”

### 第 1 步：重述问题（5–10 分钟）

把客户原话翻译成可交付的问题陈述。客户说“看住每一单、每一笔赔付、每个阿姨、每个客户”，再加上一句“我不知道那个亏的到底亏在哪”。前四句是数据入口，最后一句才是真问题。

产出：`docs/00-问题重述.md`。答辩时一句话带过：“我先确认客户买的不是报表，是一个能解释亏损的账。”

### 第 2 步：诊断（10–35 分钟）

诊断不是写报告，是把模糊抱怨变成可计算的账。做法是三步：

1. 六个痛点逐条量化，每个都写“现状数字、后果、根因、不管会怎样”；
2. 青秀和西乡塘同口径对照，锁定 13 个点的毛利率差；
3. 把 3.38 万拆成赔付 1.40、返工 1.30、空跑 0.68，并验证 9% + 13 点正好等于青秀的 22%。

产出：`docs/01-诊断报告.md`。这一步是整条证据链的价值锚，后面所有功能都在为它服务。

答辩时一定要主动说一句：“诊断里我标了三个口径矛盾：3.2 万赔付是不是全量、青秀固定成本是反推的、原文说‘同样规模’但营收其实是 2 倍。这些我没有藏，全部写在附注里。”

### 第 3 步：定范围与契约（35–55 分钟）

范围不是拍脑袋，是找“最小完备集”。5 个模块少一个，片区账就算不准；多一个，8 周就做不完。RICE 排序决定价值密度，但排期要按依赖走：M1 工单是 M2、M3、M5 的硬前置，所以先做。

同时把 10 项 out-of-scope 写死：客户小程序、阿姨 App、实时 GPS、智能派单、AI 图像定责、真实支付短信、多租户、其余 6 片区上线、14 个月历史全量迁移、财务系统对接。每一项都写“为什么不做、本期替代、什么时候做”。

产出：`docs/02-方案与PRD.md`，包含 EARS 需求、A1–A10 验收断言、假设清单。

答辩口径：“范围小不是能力小，是我主动把 8 周内做不完的东西挡在门外，保证交付可验收。”

### 第 4 步：定架构与规则（55–70 分钟）

先把约束钉死，再选型：180 分钟现场可运行、不能接真实账号、业务规则必须可单测、数据全部虚构、要能复制到下一个客户。

然后做四个关键决策：

- 技术栈用已装的轻栈：Vite + React + 纯 JS + Vitest，零后端、零状态库、零图表库；
- 业务规则全部放 `src/domain/` 纯函数，UI 只做展示；
- 金额一律整数分，时间统一 `Asia/Shanghai`，写操作全部带幂等键；
- 派生数据不持久化，损益和提成由 selectors 实时重算，避免“缓存账”和“明细账”打架。

一句话架构观：“把可变的部分放 JSON 和 store，把不可变的规则放纯函数，把演示的部分做成桩。”

产出：`docs/03-架构与选型.md`，包含数据模型、函数签名、状态机、纯函数红线、迁移路径。

### 第 5 步：组织执行（70–140 分钟）

我不是让 Agent 随便写，而是给每个 Agent 一份自包含 brief：客户背景、数字口径、技术栈、文件所有权、验收标准。主线程只收 250 字以内的结构化摘要，避免上下文污染；并行上限 2–3 个；合并后由我统一跑 `npm run verify`。

按 S0–S5 分段时间盒：开题与仓库、诊断、方案、实现、测试与就绪、交付。每个里程碑必须 commit 并 push，对应任务书第 7 条硬规定。

产出：`src/**` 五个模块、`dev-team/Agents/` 八个 Agent 定义、`docs/06-过程记录.md`。

答辩口径：“Agent 是执行单元，不是背锅侠。我用文件所有权、结构化回传、提交记录和统一门禁，证明它干了什么、干得对不对。”

### 第 6 步：验证（140–160 分钟）

验证不是“跑一遍测试”，是三条证据：

1. **自动断言**：143 例测试，A1–A10 逐条映射；
2. **对账闭合**：西乡塘 −2,660,000 分、青秀 +2,440,000 分、合计 −220,000 分，`balanced=true`；
3. **人工演示**：按 README 的五分钟脚本走核心流和错误流。

同时如实写缺口：没有覆盖率工具、没有浏览器 E2E、没有真实鉴权、SSR 冒烟只证明“可渲染”不证明“可点击”。

产出：`docs/05-测试与就绪记分卡.md`，总档 Bronze，短板明确写“无鉴权、无指标”。

答辩口径：“我不自封 Silver。Bronze 的判据是核心流跑通、错误不致命、出错看得见、可回退，这四条我认；Silver 的前置项我也写清楚了。”

### 第 7 步：商业与连续性（160–180 分钟）

商业方案只回答四个问题：45 万怎么收、现金安不安全、客户值不值、我倒下怎么办。

关键数字要能脱口而出：报价 45 万拆成诊断 3 + 底座 9 + 模块 28 + 部署培训 5；人月产出基准 20.45 万，最坏口径 15.0 万；复用率 68.5%；第 3 个同业态客户 3 天；现金流最坏 S3 时点账面 8.6 万，扣掉 7 万返工预留还剩 1.6 万，不为负。

连续性要讲得诚实：“交付不停”成立，因为范围、价格、上线标准已写死，代码 + Agent 库 + SOP 可交接，48 小时能复现；“经营不停”不完全成立，客户关系、范围变更报价、重大事故定责这三件事仍然只能等我。

产出：`docs/04-商业方案.md`、README、`docs/06`。

### 第 8 步：交付与复盘

交付不是交代码，是交一套别人能接手的东西：README 写清快速开始和演示脚本，docs/06 写清做过什么、为什么、怎么验证、哪些没做，Agent 库补齐“职责边界 / 工作流 / 输入输出 / 知识库引用 / 自检清单”五段，最后确认远端仓库可查。

答辩收尾一句话：“这次交付里，最值钱的不是五个页面，是这套换人能复现、换客户能复用的流程。”

## 四、答辩主线：三句话打底

建议开场就用这三句，把老师的注意力从“功能多少”拉到“方法和证据”：

1. **我做的不是一套报表，是一条从客户原话到亏损可解释的证据链。**
2. **我卖的不是 8 周工时，是一套换人能复现、换客户能复用的交付系统。**
3. **我敢讲的不是“全做完了”，而是“每一分钱怎么算、哪一步没做、为什么不做”。**

## 五、老师最可能问的 10 个问题

### Q1：为什么只做 2 个片区、5 个模块？是不是做得太少？

**他想确认**：你会不会为了显得做得多而失控。

**建议答法**：客户原话就是“先做 2 个片区，8 周给我看”。5 个模块是 4 个数据入口加 1 个出口，少一个片区账就算不准，多一个 8 周就做不完。RICE 排的是价值密度，不是交付顺序；M1 是硬前置，所以先做。其余 6 个片区是配置项，第 3 个同业态客户 3 天可上线，不是放弃。

**注意**：不要说“8 个片区做不了”，要说“本期用 2 个片区做对照，验证可复制”。

### Q2：你怎么证明西乡塘“亏在哪”，而不是做了一堆报表？

**他想确认**：你有没有真正的归因能力。

**建议答法**：三层证据。第一层数字闭合：26 − 20.28 − 3.38 − 5 = −2.66 万，误差 0；第二层对照解释：9% + 13 点 = 22%，13 个点正好由赔付 5.4 + 返工 5.0 + 空跑 2.6 解释；第三层动作可模拟：三项各降 30% / 25% / 40%，净利从 −2.66 收到 −1.643 万，页面标注“假设，不写回原账”。

**注意**：不要顺势说“上了系统就能扭亏”。要主动补一句：“三项全堵也只有 +0.72 万，因为它单量只有青秀一半、固定成本已经 5 万。系统能止血，不能替客户解决规模和固定成本结构。”

### Q3：这些数据是不是你编的？怎么保证不是“为了好看”？

**他想确认**：你的数字有没有可复现的证据。

**建议答法**：数据全部虚构，这是任务书要求；但口径和算式是真的。种子由固定随机种子 `20261031` 生成，没有 `Math.random()` 和 `Date.now()`；`SEED_TARGETS` 是唯一规模事实源；A1/A2 直接用种子断言；页面有“重置演示数据”，刷新和重置结果一致。凡是推算的数字，文档里逐条标了“推算”；凡是题面矛盾，附注里逐条写了。

**注意**：不要说“数据是真的”。正确说法是“数据是虚构的，但每一个数字要么来自题面，要么标注为推算，要么被测试锁死”。

### Q4：你说 AI Native、L3，代码到底是不是你自己写的？Agent 到底干了什么？

**他想确认**：你是不是把“用 AI 补全”包装成了“AI Native”。

**建议答法**：先给定义：L3 是“AI 干活、人管判断”，判据是“我请假两周，交付不停”，不是“零人工”。再给证据：8 个 Agent 都有五段正文；S0–S5 有时间盒和产出；每个 Agent 有自包含 brief 和文件所有权；主线程只收 250 字摘要；每个里程碑有 commit；docs/06 记录了偏差。人做的是搭骨架、定契约、做门禁、验收；Agent 做的是模块实现、测试补齐、文档初稿。

**注意**：不要吹“全自动”。老师一追问“Agent 怎么证明”就容易露馅。可以主动交底一个真实细节：“M2 页面 Agent 中途 502 了，但文件已完整写入且构建通过，后来被 S4 的 SSR 冒烟和选择器集成测试覆盖住了。”这种细节比空喊 L3 更有说服力。

### Q5：为什么不用 TypeScript、后端、数据库、真实鉴权？是不是偷懒？

**他想确认**：你的选型有没有约束意识，还是只会做 demo。

**建议答法**：约束先行。180 分钟现场可运行、不能接真实账号、规则必须可单测、要能复制，这四条决定了轻栈。这个项目 95% 的复杂度在业务规则和数据归集，不在请求和并发；把后端拿掉，复杂度集中到纯函数，反而更可控。生产化路径写在 docs/03 第 7 节：FastAPI/PostgreSQL、真实登录、E2E、多租户，触发条件也写了。

**注意**：不要说“不需要鉴权/后端”，要说“本期是单机试点演示，明确不承诺生产并发与安全；生产化前置项已列在记分卡和迁移路径里”。

### Q6：提成、损益、定责这些规则，怎么保证算对？

**他想确认**：你有没有工程上的正确性保障。

**建议答法**：四个抓手。金额一律整数分，避免浮点误差；账期统一 `Asia/Shanghai`，按 `completed_at` 归属；写操作全部带幂等键，重复提交和重复审批只入账一次；状态机不可跳步，缺签字不能完成。规则全部是纯函数，不读时钟、不读随机、不碰 React 和 store；A1–A10 逐条断言，143 例全绿，损益有 `balanced` 字段做分项与净利闭合校验。

**注意**：不要说“143 例等于全覆盖”。主动说：“没有覆盖率工具、没有 DOM E2E，这两项是明确缺口；我用 A1–A10 映射和 SSR 冒烟替代，不冒充 Silver。”

### Q7：赔付定责为什么“自动永不返回无责”？40% 无法定责怎么降？

**他想确认**：你懂不懂业务里的“责任”边界。

**建议答法**：自动路径永不返回 `none`，是为了防止系统默认“各打五十大板”。无责只能人工判定并填理由，这样 40% 无法定责才会真正暴露，而不是被系统洗成 0。定责用证据分：签到完成时间、服务前后照片、客户签字、投诉时效、前后对比，六项加权；40–70 分进入人工复核，70 分以上且投诉在 72 小时内才判阿姨；金额超 500 元升级财务；同一阿姨同类历史 ≥2 次只标注不直接改判；定责结果不自动扣款，只给追偿建议，且不超过当月提成 30%。

**注意**：如果老师问“为什么不用 AI 图像定责”，答：“8 周内无法证明准确率，错误定责会直接引发赔付纠纷；规则 + 人工复核更可验收，图像定责放三期，前提是至少 6 个月历史样本。”

### Q8：45 万、20.45 万/人月、68.5% 复用、3 天上线，是不是拍脑袋？

**他想确认**：你的商业数字有没有算式和边界。

**建议答法**：45 万是价值锚不是工时锚：西乡塘已经亏了 37.24 万，满产可回收 47.8 万/年，合同额只占客户年营收 1.56%。人月产出基准 45 ÷ 2.2 = 20.45 万；最坏把一次完整返工算进去，45 ÷ 3.0 = 15.0 万，恰好过线。复用率按人日算 35.6 ÷ 52 = 68.5%，代码行口径 67.7%，Agent 件数口径 85.7%，三种口径都过 60%。3 天只承诺同业态，前提是规则不新增、主数据完整、第 3 天客户能参加 UAT；主数据通过率低于 90% 就顺延，不硬上。

**注意**：不要说“45 万很便宜”。要说“传统外包同价需要 18 人月，我们 2.2 人月，提效来自复用和 Agent，不是熬夜”。3 天也不要跨业态乱承诺。

### Q9：你哪些没做？如果老师挑 1800 单、无 E2E、无鉴权、无覆盖率，怎么答？

**他想确认**：你会不会藏短板。

**建议答法**：主动交底，比被问出来好。没做的包括：真实鉴权/RBAC、后端和数据库、短信支付地图、浏览器 DOM E2E、覆盖率采集、账期锁定与红冲、批量派单、移动端、真实导出审计；工单 1800 而不是 5200，是为了演示和测试速度，营收和漏损口径不变，A1/A2 不受影响；2026-10 之外的历史只有汇总表，没有逐期明细断言。为什么不做：180 分钟、不能接真实凭据、本期是 8 周试点，价值在诊断和规则，不在生产级基础设施。每项的二期触发条件写在 docs/03 第 7 节和 docs/05 第 6 节。

**注意**：不要用“后面会补”搪塞。要给触发条件：“多用户并发或数据超过 10 万单，才迁后端；安全评审通过，才上真实登录；引入 Playwright 后，才承诺交互回归。”

### Q10：你病倒两周公司真的不停吗？如果现场给你加需求/改口径，你怎么办？

**他想确认**：你的连续性是口号还是有机制。

**建议答法**：连续性靠三样资产：代码库、Agent 库、SOP。范围、价格、上线标准在合同里写死；每个模块有 spec、Agent playbook、测试夹具；`npm run verify` 是硬门禁；换一个会写代码的人只读文档，48 小时能完成构建、测试、部署、跑通 E2E。但要诚实：**“交付不停”成立，“经营不停”不完全成立**，客户关系、范围变更报价、重大事故定责这三件事仍然只能等我。

现场加需求，先判断是“配置、规则还是新模块”：配置走配置，规则走变更单（2–5 万/条），新模块 4–8 万/个；不现场改代码，180 分钟后新增修改不计分。如果老师只是改一个演示数字，先问“这是口径变更还是演示假设”，再用“重置演示数据”回到基线，避免把演示数据改脏。

**注意**：不要现场热补代码。演示前先跑 `npm run verify`、点一次“重置演示数据”、准备好 `dist` 和离线依赖；如果真出问题，用测试输出和文档兜底，不要慌着改。

## 六、现场演示建议与总注意事项

### 6.1 五分钟演示顺序

| 时间 | 动作 | 要证明的事 |
| --- | --- | --- |
| 0:00–0:40 | M5 总览：西乡塘 −2.66 万、青秀 +2.44 万、合计 −0.22 万 | 结论先给，不绕功能 |
| 0:40–1:50 | 点赔付 1.40 万下钻 → 切青秀对照 → 拖堵漏模拟 | 亏损可解释、可下钻、可模拟 |
| 1:50–2:50 | M1 新建单 → 不签字点完成被拒 → 补签完成 | 成功流 + 错误流 |
| 2:50–3:40 | M2 新建赔付 → 评估 → 审批 → 再点一次幂等 | 定责与幂等 |
| 3:40–4:20 | M3 逐单提成 + 质量系数覆盖；M4 客户 360 + 脱敏 | 算得清、看得住 |
| 4:20–5:00 | 重置数据 + 展示 `npm run verify` 输出 + 边界声明 | 可复现、不藏短板 |

### 6.2 答辩总原则

1. **先结论后功能。** 老师时间有限，先给“亏在哪”的答案，再解释怎么做到的。
2. **不把虚构说成真实。** 客户是教学虚构，数据是种子生成；真实试点需要客户签字 UAT。
3. **不把 Agent 说成全自动。** 人做判断和验收，Agent 做执行；L3 的判据是“换人能复现”，不是“零人工”。
4. **不把假设说成事实。** 直接成本率 78%、青秀漏损 0、改善幅度 30/25/40，都是假设或对照口径，主动标注。
5. **不用功能数量证明价值。** 用“3.38 万拆解 + 13 点解释 + 对账 0 元差 + 可下钻”证明价值。
6. **主动交底偏差。** 技术栈从 TS/Zustand 改回轻栈、文档路径曾失真、工单从 5200 降到 1800、M2 Agent 中途 502，这些都在 docs/06 里，讲出来比被问出来加分。
7. **不现场改代码。** 180 分钟后不计分；演示前 reset、verify、准备离线包。
8. **留一个“诚实边界”的收尾。** 比如：“这套东西现在能证明亏损、能算清账、能复制；但它还不是生产系统，缺鉴权、缺并发、缺真实数据接入，这三项是我二期要补的。”
