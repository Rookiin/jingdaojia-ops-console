# 净到家保洁 · 架构与选型

> 数据声明：全部模型、种子数据、金额均为**教学虚构**，不含真实客户数据、账号或凭据。本文的函数签名与公式是**实现契约**，`src/domain/` 必须按此实现，测试必须覆盖每个边界。
>
> 上游：`docs/02-方案与PRD.md`（范围与 EARS 验收）。本文回答"用什么建、建什么形状、怎么证明它跑通"。

## 0. 一页架构结论

| 项 | 决策 | 理由（一句话） |
| --- | --- | --- |
| 前端 | Vite 8 + React 19 + TypeScript 5.9 | 180 分钟试点要"秒开、零后端、可单测"；SPA 足够 |
| 状态/持久化 | Zustand 5 + `persist`（localStorage） | store 层模拟持久化，刷新不丢演示数据，零数据库 |
| 数据 | 本地 JSON 种子 + Zod 4 校验 | 确定性、可复现、可审计；换客户只换 JSON 与配置 |
| 业务规则 | `src/domain/` 纯函数（无 React/无 store/无 `Date.now`） | 提成、损益、定责可单测、可重算、可回归 |
| 图表 | Recharts 3 | 声明式、与 React 19 兼容、无需额外图表服务 |
| 测试 | Vitest 5 + Testing Library 16 + jsdom 31 | 与 Vite 同源，纯函数毫秒级回归 |
| 明确不引入 | 后端服务、数据库、ORM、云账号、真实支付 | 属于 02 文档 out-of-scope；凭据零暴露 |

**一句话**："把可变的部分（数据、配置）放进 JSON/store，把不可变的部分（规则）放进纯函数，把演示的部分（通知/支付）做成桩。"

## 1. 技术选型

### 1.1 约束（先钉死，再选型）

| 约束 | 含义 | 对选型的影响 |
| --- | --- | --- |
| 180 分钟现场可运行 | 评委从零 `npm ci` 到看到结果 | 不能依赖云数据库、不能要求后端进程、不能要求真实账号 |
| 业务规则必须可单测 | 提成/损益/定责要有证据 | 规则必须与 UI、store、时间源解耦 |
| 数据全部虚构 | 不能接真实系统 | 种子 JSON 即数据源；外部服务全部 `stub` |
| 8 周 5 模块 | 迭代速度优先 | 组件与数据模型要能复用；拒绝过度设计 |
| 可复制到第 3 个客户 | 配置为主 | 片区/计价/科目/系数均须配置化，不硬编码 |

### 1.2 为什么是 Vite + React（而不是 Next.js / 小程序 / 后端渲染）

| 方案 | 优点 | 在本项目的致命点 | 结论 |
| --- | --- | --- | --- |
| **Vite + React SPA** | 冷启动 <1s、构建简单、静态部署、组件生态成熟 | 无 SSR/SEO（内部台账不需要） | **选用** |
| Next.js 14+ | SSR、路由约定、可接 API | 需要 Node 运行时/部署平台；对单机演示是额外复杂度 | 不选 |
| 微信小程序 | 贴合客户下单习惯 | 需要 AppID/审核/真机；考核禁止真实账号 | 不选（二期客户侧） |
| FastAPI + PostgreSQL | 真实并发、事务 | 180 分钟内多一个进程与迁移；规则测试仍要单独写 | 不选（二期迁移目标） |

**关键判断**：本项目 95% 的复杂度在**业务规则与数据归集**，不在请求/并发。把后端拿掉，复杂度集中到可测试的纯函数，反而更可控。

### 1.3 为什么是本地 JSON + store 层（而不是 IndexedDB / SQLite / Mock API）

| 方案 | 演示可复现 | 状态变更可见 | 实现成本 | 结论 |
| --- | --- | --- | --- | --- |
| JSON 种子 + Zustand persist | 高（重置即回到基线） | 高（同一 store） | 低 | **选用** |
| IndexedDB | 中（需清理工具） | 中 | 中 | 不选 |
| SQLite（wasm） | 中 | 低（SQL 黑盒） | 高 | 不选 |
| MSW Mock API | 高 | 中（异步） | 中 | 二期接后端时用 |

**边界**：localStorage 单浏览器、单用户、约 5MB；本期种子数据控制在 ~2MB。真实多用户/并发不在本期承诺内。

### 1.5 已知坑（写入规格，事前规避）

| # | 坑 | 硬约束 |
| --- | --- | --- |
| P1 | 浮点金额误差（0.1+0.2） | 金额一律以**分**为整数存储与计算；仅显示层除以 100；禁止 `parseFloat` 后直接累加 |
| P2 | 时区导致跨月归属错误 | 所有时间存 `ISO8601 +08:00`；账期用 `Asia/Shanghai` 的 `completed_at` 判断；禁止用浏览器本地时区 |

| P5 | localStorage 旧版本 schema 崩溃 | `persist` 设 `version` + `migrate`；解析失败 → 清空并重新注入种子，给出提示 |
| P6 | JSON 导入类型漂移 | 所有种子经 Zod `.parse()`；失败信息必须含文件名与字段路径 |
| P7 | 返工单重复计营收 | `order.is_rework=true` 的单不计营收、不计单量提成，只计 50% 工时工资 |
| P8 | 规则函数读取当前时间导致测试不稳定 | 纯函数不调用 `Date.now()`；当前时间/账期由参数注入 |
| P9 | 图表空数据报错 | 空数组返回空态，不渲染 Recharts；分母为 0 返回 `null` 而非 `NaN` |
| P10 | 导出 CSV 中文乱码 | 导出加 UTF-8 BOM；金额列用元、两位小数 |

## 2. 数据模型

### 2.1 实体关系

```
district (片区)
  ├─1:N─ cleaner (阿姨)
  ├─1:N─ customer (客户)
  ├─1:N─ order (工单)
  │        ├─N:1─ customer
  │        ├─N:1─ cleaner
  │        ├─1:N─ compensation (赔付)
  │        ├─1:N─ complaint (投诉)
  │        ├─1:0..1─ rework_record (返工)   [扩展]
  │        └─1:0..1─ idle_run_record (空跑) [扩展]
  └─1:N─ compensation（冗余 district_id，便于按片区归集）
complaint ─0..1─ compensation（一起投诉最多结一笔主赔付，允许多笔部分赔付）
cleaner ─1:N─ settlement_line（结算行，按账期） [扩展]
```

**归集规则（损益的唯一入口）**：
- 营收：`order.amount`，条件 `status ∈ {completed, closed}` 且 `completed_at` 在账期内，且 `is_rework=false`。
- 直接成本：按片区配置 `direct_cost_rate` × 营收（首版），二期改为逐单 `order.direct_cost`。
- 赔付：`compensation.amount`，条件 `approved_at` 在账期内。
- 返工：`rework_record.cost`（首版 = 返工单工时成本 + 耗材，配置估算）。
- 空跑：`idle_run_record.cost`（调度交通 + 阿姨空等补偿）。
- 固定成本：`district.fixed_cost_monthly`（账期配置）。

## 3. 关键业务规则：纯函数契约

### 3.1 通用约定

```ts
// src/domain/money.ts
export type Cents = number;                 // 整数分
export type Ratio = number;                 // 0–1
export const yuan = (c: Cents): number => c / 100;
export const roundHalfUp = (n: number): Cents => Math.round(n); // 输入已是分
export const sumCents = (xs: Cents[]): Cents => xs.reduce((a, b) => a + b, 0);
export const clamp = (n: number, lo: number, hi: number) => Math.min(hi, Math.max(lo, n));
```

- 所有函数**纯**：相同输入必得相同输出；不读全局、不读时钟、不写 store、不抛非预期异常。
- 时间由参数传入（`now`、`period`），不调用 `Date.now()`。
- 金额参数与返回值统一为 `Cents`（分）；文档公式用"元"表述，实现时 ×100。
- 除零返回 `null`（比率类）或 0（金额类），并在 `warnings[]` 中记录。

### 3.2 提成计算

```ts
// src/domain/commission.ts
export interface CommissionInput {
  orderId: string;
  cleanerId: string;
  amount: Cents;           // 订单金额
  checkinAt: string;       // ISO +08:00
  completedAt: string;     // ISO +08:00
  hourlyRate: Cents;       // 分/小时
  baseRate: Ratio;         // 单量提成率，0–1
  qualityCoef: number;     // 0.8–1.2
  isRework: boolean;
  isCancelled?: boolean;
}

export interface CommissionResult {
  minutes: number;          // 计费分钟（15 分钟向上取整，30–480 封顶）
  hourlyPay: Cents;
  orderPay: Cents;
  basePay: Cents;           // 基础提成
  qualityPay: Cents;        // 质量调整（可正可负）
  total: Cents;             // 应发（不含扣款）
  warnings: string[];
}

export function calcCommission(i: CommissionInput): CommissionResult;
```

**公式**：

```
rawMinutes   = max(0, completedAt − checkinAt) / 60000
minutes      = clamp(ceil(rawMinutes / 15) × 15, 30, 480)
hourlyPay    = round(minutes / 60 × hourlyRate)
orderPay     = round(amount × baseRate)
basePay      = hourlyPay + orderPay
qualityPay   = round(basePay × (qualityCoef − 1))
total        = basePay + qualityPay
```

**返工规则**：`isRework=true` 时 `hourlyPay × 50%`、`orderPay = 0`，`qualityPay` 按调整后 `basePay` 计算；避免用返工刷提成。

**边界与错误**：

| 条件 | 行为 |
| --- | --- |
| `completedAt ≤ checkinAt` | `minutes=30`，`warnings+=['时间异常，按最低 30 分钟']` |
| `rawMinutes > 480` | `minutes=480`，`warnings+=['超 8 小时，按 480 分钟封顶']` |
| `qualityCoef` 缺失/非数 | 按 1.0 计算，`warnings+=['质量系数缺失，按 1.0']` |
| `qualityCoef ∉ [0.8,1.2]` | 截断到边界，`warnings+=['质量系数越界已截断']` |
| `isCancelled=true` | 返回全 0，`minutes=0`，不抛错 |
| `amount < 0` / `baseRate ∉ [0,1]` / `hourlyRate < 0` | 抛 `INVALID_INPUT`（程序错误，应被 Zod 提前拦截） |

**算例（种子验收值）**：120 分钟、25 元/小时、订单 150 元、提成率 15%、质量系数 1.05：
`hourlyPay=50.00`、`orderPay=22.50`、`basePay=72.50`、`qualityPay=3.63`、**`total=76.13` 元**（7,613 分）。

### 3.3 质量系数

```ts
// src/domain/quality.ts
export interface QualityInput {
  orders: number;            // 账期内已完成单量
  onTimeOrders: number;      // 按预约时间 ±15 分钟到岗的单量
  complaintCount: number;    // 有效投诉数
  reworkCount: number;       // 返工单数
  manualOverride?: number | null;
}

export interface QualityResult {
  coef: number;              // 0.80–1.20，两位小数
  onTimeRate: number | null;
  complaintRate: number | null;
  reworkRate: number | null;
  source: 'calculated' | 'override' | 'default';
  warnings: string[];
}

export function calcQualityCoef(i: QualityInput): QualityResult;
```

**公式**：

```
onTimeRate    = onTimeOrders / orders
complaintRate = complaintCount / orders
reworkRate    = reworkCount / orders
raw = 1 + 0.20 × (onTimeRate − 0.90) − 0.50 × complaintRate − 0.30 × reworkRate
coef = round2(clamp(raw, 0.80, 1.20))
```

**边界**：

| 条件 | 行为 |
| --- | --- |
| `orders = 0` | `coef=1.00`，`source='default'`，各 rate = `null` |
| `manualOverride` 非空 | 直接采用并截断到 [0.8,1.2]，`source='override'` |
| 任一计数 > orders | 截断到 orders，`warnings+=['计数异常']` |
| 计算值为 NaN | 回退 1.00，`warnings+=['计算异常']` |

**设计意图**：按时率 ±0.02（90%→100% 仅 +0.02）、投诉与返工为负向且权重更高，保证"干好干坏不一样，但一个人不会因一次投诉被一票否决"。

### 3.4 片区损益（项目核心公式）

```ts
// src/domain/pnl.ts
export interface DistrictPnlInput {
  districtId: string;
  period: string;            // '2026-10'
  revenue: Cents;            // 已完成、非返工订单金额
  directCost: Cents;         // 阿姨工时 + 耗材 + 交通（首版 = revenue × directCostRate）
  compensation: Cents;       // 已审批赔付
  reworkCost: Cents;         // 返工成本
  idleRunCost: Cents;        // 空跑/改约成本
  fixedCost: Cents;          // 片区月固定成本
}

export interface DistrictPnlResult {
  revenue: Cents;
  directCost: Cents;
  grossProfit: Cents;        // 干净毛利 = revenue − directCost（未扣三项损耗）
  compensation: Cents;
  reworkCost: Cents;
  idleRunCost: Cents;
  leakTotal: Cents;          // 三项漏损合计
  fixedCost: Cents;
  netProfit: Cents;
  grossMarginPct: number | null;
  netMarginPct: number | null;
  leakPct: number | null;    // leakTotal / revenue
  balanced: boolean;         // 分项合计与净利差异 ≤ 1 分
}

export function calcDistrictPnl(i: DistrictPnlInput): DistrictPnlResult;
```

**公式（管理口径）**：

```
grossProfit = revenue − directCost
leakTotal   = compensation + reworkCost + idleRunCost
netProfit   = grossProfit − leakTotal − fixedCost
            = revenue − directCost − compensation − reworkCost − idleRunCost − fixedCost
```

> **与任务约束写法的口径对齐**：任务约束记为"营收 − 毛利 − 赔付 − 返工 − 空跑 − 固定成本 = 净利"。财务报表里的"毛利"**已扣过赔付/返工/空跑**（西乡塘报告毛利率 9% 即含这三项），若直接再减会重复扣减。因此本方案把该扣除项正名为**直接成本**（营收 − 直接成本 = 干净毛利 22%），数值上等价、口径唯一。两种写法互相换算：
>
> - 财务口径：`净利 = 报告毛利(9%×26=2.34) − 固定成本(5) = −2.66 万`
> - 管理口径：`净利 = 干净毛利(22%×26=5.72) − 赔付(1.40) − 返工(1.30) − 空跑(0.68) − 固定(5) = −2.66 万`
>
> 二者结果必须一致，差异 0 分；`balanced` 字段即对此做断言。

**对账校验（种子必须通过）**：

| 片区 | 营收 | 直接成本 | 干净毛利 | 赔付 | 返工 | 空跑 | 固定 | 净利 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 西乡塘 | 26.00 万 | 20.28 万 | 5.72 万（22.0%） | 1.40 | 1.30 | 0.68 | 5.00 | **−2.66 万** |
| 青秀 | 52.00 万 | 40.56 万 | 11.44 万（22.0%） | 0 | 0 | 0 | 9.00 | **+2.44 万** |

**边界**：

| 条件 | 行为 |
| --- | --- |
| `revenue = 0` | 比率返回 `null`，`netProfit = −(直接成本+漏损+固定)`，不抛错 |
| 任一输入为负 | 抛 `INVALID_INPUT`（负数只能通过红冲记录表达） |
| `directCost > revenue` | 允许（亏损），`grossProfit` 为负，`warnings` 提示 |
| 跨月订单 | 不在函数内处理；由调用方按 `completed_at` 归期 |
| 分项与净利差 >1 分 | `balanced=false`，UI 阻断导出并显示差异 |

### 3.5 堵漏模拟（敏感性）

```ts
// src/domain/pnl.ts
export interface LeakScenario {
  compensationDrop: Ratio;   // 0–1
  reworkDrop: Ratio;         // 0–1
  idleDrop: Ratio;           // 0–1
}
export function simulateLeakReduction(
  base: DistrictPnlResult,
  s: LeakScenario
): DistrictPnlResult & { assumed: true };
```

**公式**：

```
newComp   = round(compensation × (1 − compensationDrop))
newRework = round(reworkCost  × (1 − reworkDrop))
newIdle   = round(idleRunCost × (1 − idleDrop))
newNet    = grossProfit − (newComp + newRework + newIdle) − fixedCost
```

**边界**：三个 `Drop` 截断到 [0,1]；`assumed=true` 必须在 UI 显著标注"假设，不写入原始账"；比例 0 时结果必须与 base 完全一致（测试断言）。

**验收算例**：西乡塘 `comp −30% / rework −25% / idle −40%` →
`0.42 + 0.325 + 0.272 = 1.017 万/月`，`newNet = −1.643 万/月`。

### 3.6 赔付定责

```ts
// src/domain/responsibility.ts
export type Responsibility = 'cleaner' | 'customer' | 'product' | 'none' | 'undetermined';

export interface ResponsibilityInput {
  order: {
    id: string;
    checkinAt: string | null;
    completedAt: string | null;
    photosBefore: string[];
    photosAfter: string[];
    signature: string | null;
  };
  complaintAt: string;              // ISO +08:00
  claimAmount: Cents;
  hasCustomerPrePhoto: boolean;     // 客户提供了服务前已有损坏的照片
  productDefectEvidence: boolean;   // 耗材/设备缺陷证据
  priorSameTypeCount: number;       // 该阿姨近 90 天同类赔付次数
  source: 'auto' | 'manual';
  manualReason?: string;            // source='manual' 时必填
}

export interface ResponsibilityResult {
  responsibility: Responsibility;
  evidenceScore: number;            // 0–100
  reasons: string[];                // 每条规则命中说明
  requiresManualReview: boolean;
  maxApprovalRole: 'district_manager' | 'finance'; // 审批层级
}

export function decideResponsibility(i: ResponsibilityInput): ResponsibilityResult;
```

**证据评分（0–100）**：

| 代码 | 证据 | 分值 |
| --- | --- | ---: |
| E1 | 有签到与完成时间 | 15 |
| E2 | 有服务前照片 ≥1 张 | 15 |
| E3 | 有服务后照片 ≥1 张 | 15 |
| E4 | 有客户签字 | 15 |
| E5 | 投诉在完成后 72 小时内 | 20 |
| E6 | 前后照片可对比且差异指向损坏 | 20 |

**判定顺序（先命中先返回，保证确定性）**：

| 顺序 | 条件 | 结果 | 复核 |
| --- | --- | --- | --- |
| 1 | `source='manual'` 且 `manualReason` 非空 | 采用人工值 | 记录理由；"无责"仅能由此路径产生 |
| 2 | `productDefectEvidence=true` | `product` | 否 |
| 3 | `hasCustomerPrePhoto=true` 且无服务窗内新增损坏证据 | `customer` | 否 |
| 4 | `score ≥ 70` 且 E5 成立 | `cleaner` | 金额 >300 元需二次审批 |
| 5 | `40 ≤ score < 70` | `undetermined` | **是** |
| 6 | `score < 40` | `undetermined` | **是** |
| 7 | 以上均不命中（无损坏且客户撤销） | `undetermined` | 是（人工改"none"） |

**硬规则**：

- 自动路径**永不返回 `none`**（无责必须人工判定并填理由）。
- `claimAmount > 50000`（500 元）→ `requiresManualReview=true`，`maxApprovalRole='finance'`。
- `priorSameTypeCount ≥ 2` → 不改变责任方，但 `reasons` 标注"该阿姨同类历史 ≥2 次"。
- 同一 `orderId` 允许多笔部分赔付，但累计不得超过 `max(order.amount × 3, 300000)`（3,000 元）。
- 定责结果**不自动扣款**；仅生成"追偿建议"（≤当月提成的 30%），由财务人工处理。

**赔付金额函数**：

```ts
export function calcCompensation(input: {
  claimAmount: Cents;
  responsibility: Responsibility;
  cap: Cents;                 // 默认 300000 分 = 3,000 元
}): { payable: Cents; recoverable: Cents; warnings: string[] };
```

| 责任方 | 公司应付 | 追偿建议 |
| --- | --- | --- |
| cleaner | `min(claim, cap)` | `payable`（受 30% 月提成上限约束，由财务执行） |
| customer | 0 | 0 |
| product | `min(claim, cap)` | 向供应商追偿（系统外） |
| none | 0 | 0 |
| undetermined | `min(claim, cap)` | 0，计入无法定责率 |

## 8. 架构假设

1. 种子数据以**分**为整数；所有文档金额为元，二者换算在 `money.ts` 统一。
2. 直接成本率 0.78 为配置，非硬编码；客户确认后只改配置。
3. 青秀三项漏损在对照夹具中为 0，属基准口径；看板按实际录入计算。
4. 图片/签字以本地占位 URL 或 base64 小图模拟，不上传对象存储。
5. 时间统一 `Asia/Shanghai`；若部署到非中国时区服务器，仍以业务时区为准。
6. 本期不做离线同步/冲突合并；localStorage 单写者模型。
